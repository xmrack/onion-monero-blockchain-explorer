01 Fix these first

Ordered by exposure rather than raw severity. Findings 4 and 5 are reachable in the deployment the project's own README recommends and need no cryptographic gate; finding 21 is more severe but sits behind a flag no documented invocation sets.

Priority 1 · findings 4 & 5

Reject out-of-range indices in the tx pusher

Two unvalidated attacker-chosen indices in /checkandpush. Reject the request — do not clamp. Clamping un-masks findings 6 and 22.

Priority 2 · finding 21

Widen the truncated index parameter

Fix the bounds checks and the unsigned int width in tools.h:250. The width mismatch is the root cause; checks alone leave it reintroducible.

Priority 3 · findings 1 & 7

Guard query parameters; stop leaking view keys

One line per handler. Separately, remove the private view key from the shortcut URL — no flag is needed to reach that leak.

02 The two findings that matter most

#4 An arbitrary aligned read, printed into the response

src/page.h:2917 indexes a std::vector with tx_source.real_output, taken straight from the attacker's deserialised blob and never bounds-checked. The value read becomes a database output index, and on the lookup-failure path it is formatted into the response body.

The offset is not quantised the way the 72-byte element size suggests. Because 72 = 8 × 9 and 9 is odd, 9 is invertible modulo 264 — so every 8-byte-aligned offset is reachable, forwards and, through wraparound, backwards. A proof-of-concept solves for the index that recovers a secret planted 48 bytes before the vector:

One word of process memory per request, at any aligned address, returned in plain text. That is enough to defeat ASLR and to walk out adjacent secrets — including other users' submitted view keys, which live in the same heap.

#21 A bounds check that guards a different number than it protects

decode_ringct takes the output index as unsigned int (src/tools.h:250) while the caller forms the write target with the full 64-bit value. Monero validates the truncated parameter, then writes through the caller's reference. The two are different numbers.

Scope, stated honestly

The write displacement is quantised to 256 GiB steps, so it cannot practically be aimed at a chosen heap object on 64-bit — in nearly all cases it lands unmapped and the process dies. The dependable outcome is a guaranteed remote crash; the read primitive in finding 4 is the precisely controllable one. No path to code execution is claimed. Finding 21 ranks first on severity because it is the only finding that writes to attacker-chosen memory and because it defeats an upstream check placed there to prevent exactly this.

03 Exposure depends on flags — and the README sets them

Reachability is entirely flag-driven, so "default" here means what the project tells operators to run, not what the bare binary does. Every documented invocation (README.md:215, 312, 302) enables the pusher and the JSON API. None enables the key-image checker, the output-key checker or mixin guessing.

04 Evidence

Every finding has a proof-of-concept, in one of two tiers with deliberately different evidentiary weight.

  • Mechanism PoCs (poc/micro/, 13 programs) — self-contained C++ with no dependencies. All were compiled and executed; quoted output is real. They prove the defect, not its reachability.
  • Reachability PoCs (poc/http/, 8 scripts) — requests against a running explorer. These were not executed. The review environment has no monero libraries, so the explorer could not be built. They are derived from the code and need confirming against a real build.

Selected executed results:

Seven findings (6, 19, 22, 23, 27, 28, 32) have working mechanism PoCs but no reachable trigger in the shipped code. The PoC shows the defect is real; the reachability analysis explains why it cannot currently be driven. Keeping that distinction visible is the point of separating the tiers.

05 Corrections

Six claims did not survive verification. Four were caught by running the code, two by re-reading it. They are recorded because the reasons are more useful than the original claims were — and because an audit that only accumulates findings is not being checked.

#1  Critical → High

libstdc++ throws where I assumed it segfaults

I rated a null query parameter Critical on the assumption that std::string(nullptr) calls strlen(nullptr). It does not: the constructor has an unconditional null check that throws std::logic_error (basic_string.h:641). Crow catches it and the process survives. It would still be Critical against libc++.

#4  Oracle → direct arbitrary read

Stronger than first written

Described as an inference oracle over a 72-byte sampling. It is a direct read: the value is printed verbatim into the response, and modular arithmetic makes every 8-byte-aligned offset reachable. Proven by exact secret recovery.

#22  Critical → latent

Both claimed triggers were wrong

Path 1 cited a loop in show_my_outputs(), which never calls the affected function. Path 2 is masked by finding 4, which crashes first. My most alarming claim — reachable on the ordinary transaction page, no pusher required — was false.

#6  Critical → latent

Shares the precondition I said it didn't

On retracting 22 I asserted 6 stood independently. It does not: find_nth only fails when the point count is zero, because the preceding clamp guarantees a valid index otherwise — the same empty-timescale precondition, masked the same way.

#14  Medium → Low

The out-of-bounds read cannot happen

I claimed an unchecked gmtime_r leads strftime to index glibc's month and day-name arrays out of bounds. That needs %b or %a; the only formats used anywhere are %F %T and %F. The result is a nonsense date, not memory unsafety.

#18  Narrowed

The binary is not unmitigated

I wrote that the bare cmake .. leaves the binary without stack-protector, PIE or RELRO. Ubuntu's gcc enables all three by default. The real cost is _FORTIFY_SOURCE, which glibc disables without optimisation — 0 fortified calls at -O0 against 6 at -O2.

One dependency is easy to get wrong and worth restating: findings 6 and 22 are unreachable only because finding 4 crashes first. Fixing 4 by clamping the out-of-range index rather than rejecting the request would make both live. They must land together.

07 Method and limits

Every source file was read in full, three times: an initial pass, a verification pass aimed at falsifying the findings, and a third pass over the regions of src/page.h not yet displayed line by line. The third pass produced no new critical findings, which is itself a result.

Four limits are worth stating plainly:

  • The explorer was never built or run. No monero libraries are available in the review environment, so all reachability conclusions are static traces and the poc/http/ scripts are unverified.
  • Three claims rest on monero's source, which is not vendored here — the CHECK_AND_ASSERT_THROW_MES guard and mask write inside decodeRctSimple, and the RCT deserialiser's ecdhInfo.size() == vout.size() enforcement. Confirm these against the v0.18.4.0 tree before filing upstream.
  • src/crypto/rx-slow-hash.c (512 lines) was not audited in depth: RandomX is force-disabled at startup (main.cpp:108), so none of it is reachable. Revisit if that changes.
  • Findings 8, 14 and 26 assume an attacker who controls daemon responses. That is a different adversary from the unauthenticated web client, and it is only realistic under deployment profile B.

Nothing here was reported to any third party, and no live instance was tested. The full technical report, per-finding fix guidance and all proof-of-concept sources are on the claude/critical-vulnerabilities-61spzk branch: SECURITY_AUDIT.md and poc/.
